Decision 7 of 8

CSS consumption strategy

Technical

La limpieza no consiste solo en declarar tokens: también importa cómo los consume cada componente. Listen ya mezcla Tailwind, CSS global, variables parcialmente alineadas e inline styles. Necesitamos una regla clara que permita layouts calculados, canvas y artwork dinámico sin convertir cada caso visual en un escape hatch permanente.

Dime: “Option A” · “Option A but [cambio]” · “more options”

Option A
RecommendedChosen

CSS variables + Tailwind

.player-bar {
  color: var(--text-primary);
  background: var(--surface-panel);
}
// dynamic geometry stays inline
Usar CSS custom properties como runtime de tokens y utilities Tailwind semánticas como API de consumo. Los estilos compartidos y estados complejos viven en CSS; inline queda reservado a valores calculados —por ejemplo ancho de seekbar, coordenadas, gradients derivados o estilos del canvas— con una regla revisable. Es la opción más alineada con el stack actual.

Funciona bien cuando

  • Tailwind ya es parte del proyecto.
  • Se necesitan themes runtime.
  • Hay efectos calculados legítimos.

Vigilar

  • Hay que nombrar utilities semánticas.
  • Inline requiere allowlist clara.

Option B

Inline-first runtime styles

dynamic button
styles resolved in React
Resolver la mayoría de valores visuales en objetos de estilo React y dejar CSS para layout global. Simplifica algunos casos dinámicos, pero hace más difícil inspeccionar themes, aumenta rerenders potenciales y favorece que cada componente invente su propia semántica.

Funciona bien cuando

  • La UI es muy dinámica.
  • El runtime calcula casi todo.

Vigilar

  • Peor cacheabilidad y legibilidad.
  • Más difícil aplicar skins globales.

Option C

CSS Modules per feature

Player.module.css
local scope

tokens
Mover cada feature a CSS Modules para encapsular clases y reducir colisiones. Puede mejorar ownership local, pero añade una convención paralela a Tailwind y no resuelve por sí misma la semántica de tokens, el runtime de skins ni los estilos globales de superficies.

Funciona bien cuando

  • Hay mucho CSS feature-local.
  • Se necesita aislamiento fuerte.

Vigilar

  • Duplica formas de estilizar.
  • Transición costosa en el stack actual.
Tell me: “Option C”
Option D

CSS-in-JS engine

const style = css({
  color: token(“accent”),
  ...props
})
runtime styles everywhere
Introducir un motor CSS-in-JS para expresar tokens, variantes y estados desde React. Es potente, pero innecesario para el objetivo: añade runtime, complejidad de SSR/build y otra API de estilos que conviviría con Tailwind y CSS existente.

Funciona bien cuando

  • El runtime styling es requisito central.
  • El stack ya está basado en ello.

Vigilar

  • Más coste y superficie técnica.
  • No encaja con la dirección actual.
