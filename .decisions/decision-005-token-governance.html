Decision 5 of 8

Token governance

Technical

Un contrato de tokens solo funciona si el código nuevo no puede saltárselo sin dejar señal. Necesitamos una forma de distinguir excepciones legítimas —artwork, canvas, valores de terceros o estados calculados— de colores, sombras y opacidades copiados por comodidad. La gobernanza debe ser automática y útil para desarrollo diario, no una colección de documentos que nadie consulta.

Dime: “Option B” · “Option A but [cambio]” · “more options”

Option A

Documentation only

Token guide
review manually
Documentar nombres, usos y excepciones en Markdown, dejando la revisión en manos del equipo. Es barato y flexible, pero no protege el código cuando se añade una pantalla con prisa. El inventario volvería a ser una fotografía puntual.

Funciona bien cuando

  • El equipo es muy pequeño.
  • El cambio visual es ocasional.

Vigilar

  • No bloquea regresiones.
  • La documentación se desactualiza.

Option B
RecommendedChosen

Registry + lint guardrails

primitive tokens
semantic contract
lint + allowlist + CI
Mantener un registry pequeño y explícito de tokens semánticos, documentar excepciones en una allowlist con motivo y añadir checks que detecten nuevos colores, utilities prohibidas, inline styles problemáticos o tokens sin uso. Los checks informan con precisión y permiten excepciones justificadas. Es la mejor relación entre protección y coste.

Funciona bien cuando

  • Se quiere clean code sostenible.
  • El equipo trabaja por PRs.
  • Hay excepciones técnicas reales.

Vigilar

  • Hay que mantener la allowlist.
  • Los mensajes del lint deben ser accionables.

Option C

Generated token pipeline

source JSON
→
CSS + TS + native
Usar un pipeline de generación completo, por ejemplo con un formato agnóstico de plataforma que produzca CSS, TypeScript y otros outputs. Es una base sólida si habrá web, desktop y móvil con el mismo sistema, pero añade tooling, build steps y una capa de abstracción que no es imprescindible para limpiar Listen ahora.

Funciona bien cuando

  • Hay varias plataformas consumidoras.
  • El diseño se comparte fuera de la web.

Vigilar

  • Más infraestructura de build.
  • Puede ocultar el contrato real.

Option D

Review by convention

✓ token used
! check manually
× no automated rule
Confiar en convenciones de naming, code review y una checklist de PR sin crear tooling específico. Mantiene el repositorio simple, pero depende demasiado de la memoria de cada persona y no permite medir si el drift realmente baja con el tiempo.

Funciona bien cuando

  • El equipo cambia poco.
  • La superficie visual es pequeña.

Vigilar

  • Resultados inconsistentes.
  • Difícil detectar deuda acumulada.
