Decision 1 of 8

Token architecture

Technical

Esta decisión fija la frontera entre valores visuales, tokens semánticos y componentes. Es la base para que el aspecto actual de Listen pueda quedar congelado como default, que un skin pueda sustituir una paleta completa y que el código deje de depender de colores y efectos arbitrarios. También determina cuánto de la capa compartida puede evolucionar sin desestabilizar Admin.

Dime: “Option B” · “Option A but [cambio]” · “more options”

Mantener Tailwind como API principal y sustituir los hardcodes por combinaciones de utilities. Es la opción con menor infraestructura inicial y permite avanzar rápido en la limpieza visual, pero los skins acabarían dependiendo de convenciones implícitas y de muchas clases repetidas.

Funciona bien cuando

  • Se prioriza velocidad inmediata.
  • El conjunto visual apenas cambia.

Vigilar

  • Difícil asegurar semántica y consistencia.
  • Los skins generan combinaciones frágiles.

Option B
Recommended

Semantic token contract

primitive: cyan-500
semantic: accent-action
component: button-primary
Definir una jerarquía explícita: primitives controladas, tokens semánticos y componentes canónicos. El `default` captura los valores actuales; cada skin reemplaza solo tokens de contrato; y las excepciones dinámicas —como canvas o artwork— quedan documentadas y aisladas. Es la mejor base para limpiar Listen sin perder flexibilidad.

Funciona bien cuando

  • Se necesita tematizar sin duplicar UI.
  • Se quiere prevenir nuevo drift.
  • Admin debe poder compartir base estable.

Vigilar

  • Requiere clasificar y migrar gradualmente.
  • Hay que mantener el contrato pequeño.

Option C

Runtime theme engine

theme = “default”
skin = “neon”

--color-accent: var(...)
--surface-panel: var(...)
Construir desde el principio un motor de temas en React, con registro de skins, resolución de tokens y actualización runtime. Ofrece una API muy potente para cambiar apariencia sin recargar, pero introduce una capa de estado y complejidad que no es necesaria para corregir el drift inicial.

Funciona bien cuando

  • El cambio de skin en tiempo real es central.
  • Habrá personalización avanzada.

Vigilar

  • Más estado, hidratación y testing.
  • Puede ocultar problemas CSS reales.

Crear un sistema completamente aislado para Listen, incluso si eso duplica parte de la infraestructura compartida. Reduce el riesgo inmediato sobre Admin y permite decisiones específicas de producto, pero deja dos fuentes de verdad y contradice el objetivo de corregir el drift en los componentes compartidos.

Funciona bien cuando

  • Listen necesita una identidad radicalmente distinta.
  • Admin no puede tocarse durante meses.

Vigilar

  • Duplica mantenimiento y tokens.
  • El drift compartido permanece.

Custom choice
B+C · Chosen

Semantic contract + runtime resolver

primitive: cyan-500
semantic: accent-action
component: button-primary
runtime: skin = “default”
La arquitectura elegida combina B y C con una frontera clara. El contrato semántico define los tokens autorizados y los componentes consumen solo ese contrato; un resolver runtime ligero selecciona el theme/skin, persiste la preferencia y aplica los atributos y variables CSS. No habrá CSS-in-JS ni un motor que recalcule estilos por componente.

Decisión

  • Default actual preservado.
  • Skins intercambiables y gobernados.
  • Admin protegido por capas.

Límite explícito

  • Sin personalización arbitraria.
  • Sin resolver visual por frame.
Chosen: “B+C”
