Decision 4 of 8

Default parity

Visual

El aspecto actual de Listen debe convertirse en el theme default, pero el estado actual contiene colores equivalentes con nombres distintos, opacidades repetidas y decisiones accidentales de componentes. Esta decisión fija si la migración debe conservar cada detalle existente o preservar la identidad y la experiencia mientras normaliza la implementación. El objetivo es que los cambios intencionados sean visibles y los cambios accidentales sean detectables.

Dime: “Option B” · “Option A but [cambio]” · “more options”

Option A

Pixel freeze

Congelar visualmente cada pantalla y no aceptar diferencias apreciables durante la migración. Todo valor actual se convierte en token aunque esté duplicado. Es útil si hay snapshots visuales fiables, pero puede perpetuar decisiones inconsistentes y hacer que el nuevo contrato sea innecesariamente grande.

Funciona bien cuando

  • La paridad pixel-perfect es requisito.
  • Hay una suite visual madura.

Vigilar

  • Conserva accidentalmente el drift.
  • Complica la taxonomía de tokens.

Option B
RecommendedChosen

Perceptual parity

- #1da0c3 / #0891b2 / #06b6d4
+ --color-accent-action
same intent · one contract · tested contrast
Preservar la identidad, jerarquía, densidad y sensación del Listen actual, pero consolidar valores equivalentes bajo tokens semánticos. Se permiten pequeños cambios de implementación si mejoran contraste, consistencia o responsive; cualquier diferencia visual deliberada queda documentada. Es el equilibrio adecuado para obtener un default reconocible y código limpio.

Funciona bien cuando

  • El default debe sentirse igual.
  • Se quiere eliminar duplicación real.
  • La QA visual puede validar intención.

Vigilar

  • Hay que definir tolerancias visuales.
  • Requiere revisión de pantallas clave.

Option C

Redesign during cleanup

new nav
new cards

new player

new density
Aprovechar la migración para rediseñar el default en paralelo. Permite corregir problemas visuales de raíz, pero mezcla la definición del sistema con decisiones de producto y hace imposible saber si una regresión viene del refactor o del rediseño. Aumenta mucho el alcance.

Funciona bien cuando

  • Existe un rediseño aprobado.
  • Se acepta cambiar experiencia.

Vigilar

  • Scope y QA se multiplican.
  • Se pierde el baseline actual.
Tell me: “Option C”
Option D

Legacy layering

legacy values remain as fallback

Añadir themes y tokens por encima de la implementación actual, dejando la mayoría de hardcodes como fallback. Reduce el riesgo de la primera migración, pero mantiene dos fuentes de verdad y permite que nuevas pantallas sigan copiando el legado.

Funciona bien cuando

  • Hay una ventana de cambio mínima.
  • Se necesita un puente temporal.

Vigilar

  • El drift no desaparece.
  • El puente se vuelve permanente.
